# Acceptance Criteria Testability Audit — Draft

**Date:** 2026-10-12  
**Status:** DESK-ONLY AUDIT; NOT APPROVED.  
**Scope:** REQ-001–REQ-016 and NFR-001–NFR-010 in `CORE_REQUIREMENTS_DRAFT.md`, cross-checked against the acceptance threshold register, traceability matrix, verification strategy, voice-agent evaluation plan, requirement/contract coverage audit, consistency review and Phase 0 exit map.

This audit evaluates whether current acceptance criteria are objectively testable and what evidence would be needed later. It does **not** execute tests, approve a threshold, prove provider capability, close a legal/privacy dependency, approve the baseline or authorise implementation.

## 1. Method and status definitions

Each criterion is assessed against: identifiable actor and preconditions; action/event; observable expected outcome; negative/partial/timeout/duplicate/out-of-order/revoked/stale-state handling where applicable; evidence artifact; and any decision or numeric threshold needed before a pass/fail claim is valid.

| Audit status | Meaning |
|---|---|
| **PARTIAL** | At least one observable behavior is stated, but one or more important assertions, fixtures, boundaries or evidence rules remain underspecified. |
| **BLOCKED — EXTERNAL EVIDENCE** | A test design can be drafted, but a valid pass/fail test depends on route/provider/jurisdiction/operating evidence not available yet. |
| **NOT MEASURABLE YET** | A target or method is explicitly absent, owner approval is pending, or the criterion relies on undefined policy/threshold. |
| **CONDITIONAL / DEFERRED** | Testability is relevant only if the feature is retained in the approved MVP; it must not be silently treated as in-scope. |

No requirement is marked **PASS**, **APPROVED**, or release-ready by this audit. “Evidence artifact” means a future planned artifact, not evidence already collected.

## 4. Cross-cutting failure-path gaps

The following are important reusable scenario families. Their presence here is a test-design recommendation, not a claim that every scenario is already fully specified.

- **Partial completion:** request accepted but provider action not completed; one of multiple deletion targets remains pending; summary exists but correction/audit write fails; transfer begins but no confirmed target state arrives.
- **Timeout and ambiguity:** client times out after server-side success; provider returns no final state; delayed callback arrives after local timeout; a UI must not convert “unknown” into “off”, “deleted”, “transferred” or “complete”.
- **Duplicate/replay/out-of-order:** repeated activation/disable, repeated transfer, replayed signed callback, connect/disconnect reversal, duplicate usage event and late invoice adjustment.
- **Revoked/changed authority:** session revoked during an active request, recovery factor changed, connector scope removed, account suspended, tenant/resource binding changed.
- **Stale/conflicting state:** notification arrives late, status cache is stale, route state disagrees with provider evidence, profile changes during a session, an old event follows a terminal event.
- **Privacy/security negative cases:** cross-account identifiers, export leakage, sensitive data in logs, caller-supplied prompt injection, account enumeration, recovery abuse, unauthorized tool scope and retention expiry racing with reads.
- **Operational degradation:** provider outage/quota exhaustion, one-way/no media, queue saturation, worker restart, deletion backlog, alert delivery failure and recovery/restore failure.

For each scenario that becomes in-scope, the future test case should record: requirement ID; scenario ID; fixture/setup; event sequence; expected user-visible state; expected server/data/audit state; prohibited side effects; timeout/clock boundaries; cleanup; evidence artifact; result; build/config/provider version; and reviewer. No pass/fail result should be entered until the relevant policy, supported configuration and threshold are approved.

## 5. Threshold and evidence discipline

- AT-001–AT-012 remain governed by `ACCEPTANCE_THRESHOLD_REGISTER.md`; this audit does not change their status.
- AT-001 (2-action disable access), AT-002 (30 repetitions / 95% proposed routing), AT-004 (500 ms cancellation), AT-005 (zero duplicate ledger charges), AT-006 (zero cross-tenant unauthorized actions), and AT-007 (zero unauthorized actions) are **proposed controls/thresholds**, not approved release criteria.
- AT-003, AT-008, AT-009, AT-010 and AT-012 remain open; AT-011 has a proposed hard-cap control but amounts remain open.
- Do not invent missing thresholds, set them retrospectively after observing results, or treat “not applicable” as a default. Record an owner decision and rationale in `DECISION_LOG.md`.
- Provider-specific and legal/jurisdiction-dependent criteria cannot be marked testable-to-pass until the relevant contracts/policies are known. This is different from a missing test artifact after a requirement is otherwise measurable.
- The repository contains plans and desk reviews only. This audit did not run tests, interviews, route experiments, provider outreach, benchmarks, load tests, legal review or implementation.

## 6. Recommended sequence to improve testability

1. **Owner/policy decisions first:** select the candidate launch route/geography and MVP feature set; resolve whether takeover, transcript/audio and hospitality connectors are in scope.
2. **Close external dependencies:** obtain activity-specific approval before route tests, interviews or provider outreach; obtain qualified jurisdiction-specific review before legal/policy-dependent release claims.
3. **Define state contracts:** finalize only provider-neutral state semantics now; map them to actual provider events once route/provider evidence exists. Define timeout, stale state, partial completion and terminal-state precedence.
4. **Approve measurement contracts:** decide threshold owners, sample/denominator, environment, measurement boundaries, tolerances and release gates before any results are collected.
5. **Build traceable future test cases:** link every in-scope criterion to a named test/evidence artifact and expected negative side effects; preserve evidence provenance and version/configuration.
6. **Re-audit before baseline approval:** ensure every P0 criterion is either measurable and evidence-backed, explicitly blocked with a named dependency, or deliberately removed/deferred through owner decision. Do not use documentation completeness as a proxy for feasibility or release readiness.

## 7. Conclusion

The current requirements are useful behavioral drafts, but **none of REQ-001–REQ-016 or NFR-001–NFR-010 is declared fully testable and release-ready by this audit**. Some contain observable assertions; others depend on missing policy, thresholds, route/provider evidence, operational ownership or a deliberate scope decision. Planned verification artifacts are not executed evidence. Phase 0 remains incomplete and product implementation remains unauthorized.
