# Requirement-to-Contract Coverage Audit

**Review date:** 2026-10-12  
**Status:** Documentation audit; not owner-approved and not release evidence.  
**Scope:** REQ-001–REQ-016, mapped across proposed API operations, data/state contracts, security/privacy controls, failure scenarios and future verification artifacts.

## Executive conclusion

The current drafts have useful conceptual coverage, but **no P0 candidate is release-ready on documentation alone**. This audit distinguishes:
- **Partial** — a draft contract exists, but design detail, verification, owner decision or evidence is still missing.
- **Blocked** — route/provider evidence, legal/privacy review, or another external dependency prevents a complete contract.
- **Conditional** — only valid if the chosen route supports the capability and tests prove it.
- **Future** — outside the initial core MVP candidate; do not implement from the presence of a draft.

API operations in this table are resource-level proposals from `API_CONTRACT_DRAFT.md`, not approved endpoint names or schemas. State names are conceptual and must be mapped to the selected route/provider before implementation. The API draft now explicitly includes route-eligibility listing, owner correction of supported summary fields, and deletion-status retrieval; these are still proposals and require schema/security review.

## Cross-cutting contract gaps

| Gap | Affected requirements | Required disposition before baseline approval |
|---|---|---|
| Provider/route state mapping and supported combination evidence | REQ-001, REQ-002, REQ-005, REQ-006, REQ-007, REQ-014 | Keep route-dependent claims blocked until documented provider contracts and separately approved controlled route evidence exist. |
| Account owner versus future domain tenant | REQ-011, REQ-012 | Do not equate personal account ownership with hospitality-tenant authority; define membership, delegation and revocation before domain connectors. |
| Caller disclosure versus account-holder choice/legal consent | REQ-004, REQ-010 | Keep separate data concepts and obtain route/jurisdiction-specific review; no UI or audit label may imply consent without supporting policy/evidence. |
| Distributed deletion | REQ-010, REQ-013, REQ-015 | Define required targets, retry ownership, backup expiry, legal exceptions and the exact meaning of completed before promising a deletion SLA. |
| Usage idempotency and financial reconciliation | REQ-005, REQ-009, REQ-015 | Define key uniqueness scope, billable unit, adjustments, invoice reconciliation and safe quota behavior before paid pilot. |
| Privacy-safe observability | REQ-005, REQ-008–REQ-011, REQ-014–REQ-016 | Specify field allowlist/redaction, access and retention; test phone numbers, tokens, profile context and call content are not leaked. |
| Requirement gaps in feature scope | SCOPE-011, SCOPE-012 | Defer follow-up tasks/reminders and contact allowlist/denylist from MVP or create and review dedicated requirements before inclusion. |

## Verification evidence register

These are future verification artifacts, not tests performed in this audit:

- **V-ROUTE:** Supported route matrix, provider written support, activation/disable/restoration drill.
- **V-CALL:** Provider signature/replay contract, duplicate/out-of-order event suite, multi-leg and terminal-state reconciliation.
- **V-REALTIME:** End-to-end p50/p95/p99, barge-in/cancellation, media-loss and provider-timeout results.
- **V-DISCLOSURE:** Approved policy/version, caller disclosure scripted tests and escalation scenarios.
- **V-PROFILE:** Schema/version isolation, prompt injection and active-session change behavior.
- **V-SUMMARY:** Labelled factuality/uncertainty evaluation with negation, names, dates, missing facts and commitments.
- **V-BILLING:** Idempotent ledger, immutable adjustments, quota exhaustion and provider invoice reconciliation.
- **V-PRIVACY:** Data-flow inventory, reviewed notices, per-class retention, provider deletion, backup expiry and partial-deletion exercise.
- **V-ISOLATION:** Cross-account negative tests for APIs, search, exports, background jobs, callbacks and tools.
- **V-AUTH:** Enumeration, brute force, recovery replay, session expiry/revocation and recovery-factor compromise tests.
- **V-OPS:** Field-level log scan, alert ownership/runbook exercise, fault injection and recovery drill.
- **V-CONNECTOR:** Future only: tenant/scope authorization, idempotency, confirmation, SSRF and audit tests for each approved Antena capability.

The source verification/test plan and acceptance threshold register remain canonical for test approach and candidate thresholds. No thresholds are approved by this audit.

## Approval status

This audit closes a documentation mapping pass only. It does not close external evidence gaps, establish route feasibility, provide legal advice, approve the product baseline, authorize fieldwork or authorize implementation. Phase 0 remains incomplete. Baseline approval and implementation authorization remain separate decisions.
