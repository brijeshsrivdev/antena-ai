# Planned Acceptance-Test Catalogue — Draft

**Date:** 2026-10-13  
**Status:** PLANNING ONLY — NOT APPROVED; ALL TESTS NOT RUN.  
**Scope:** 68 original planned scenarios for REQ-001–REQ-016 and NFR-001–NFR-010, plus 18 supplemental business phone assistant scenarios (BPA-001–BPA-018) mapped to proposed REQ-017–REQ-022. All 86 scenarios remain NOT RUN; the six addendum requirements are unapproved.

This catalogue converts the testability audit and business-assistant gap audit into concrete scenario IDs, preconditions, stimuli, expected observable outcomes and planned evidence. BPA scenarios are supplemental and do not mean proposed REQ-017–REQ-022 are approved or that every new acceptance criterion is fully covered. It is a test-design artifact only: it does not establish that a route/provider supports a scenario, approve a threshold, authorize interviews or experiments, establish legal compliance, or authorize product implementation.

## 1. Execution and evidence rules

- Every row is **NOT RUN** by default. The status column identifies the blocker or decision dependency; it is not a result.
- Do not execute product-dependent scenarios before explicit implementation authorization. Do not run interviews, provider outreach, live route tests, spending or legal work without activity-specific approval.
- Before any future execution, add: test owner; approved requirement/version; build and configuration; route/provider/device/OS/plan/SIM/language; environment and fixture version; start/end timestamps; actual result; evidence link; defects; reviewer; and retest status.
- A pass requires the expected result **and** absence of prohibited side effects (duplicate billing, unauthorized access/action, false “active/off/deleted/transferred” claim, sensitive log leakage).
- A threshold-dependent test cannot pass against a proposed number until the owner approves the threshold and measurement protocol in `ACCEPTANCE_THRESHOLD_REGISTER.md`.
- Provider/jurisdiction-dependent tests remain blocked until the relevant capability contract or qualified policy review exists. A mock test proves only the mocked contract.
- Synthetic data is the default. Real caller audio/content is not permitted for test use absent separately reviewed legal basis and safeguards.
- `ACCEPTANCE_CRITERIA_TESTABILITY_AUDIT.md` remains the source for the rationale and gap classification; `ACCEPTANCE_THRESHOLD_REGISTER.md` remains the single source for candidate numeric thresholds.

## 7. Entry criteria before a scenario can be executed

1. The owner has approved the applicable scope and requirement version.
2. Required route/provider capability and supported configuration are evidenced, or the test is explicitly limited to a named mock/contract test.
3. Any legal/privacy-dependent policy is reviewed for the target jurisdiction and data flow.
4. Threshold, measurement boundary, sample/denominator and pass/fail rubric are approved before collecting results.
5. Test data, access, spend caps, rollback/recovery, logging and evidence retention are defined.
6. The test has a named responsible person and a safe stop/abort condition.

## 8. Conclusion

This is a future test plan, not verification evidence. The 68 original TC/NT scenarios and 18 supplemental BPA scenarios are all NOT RUN. Proposed REQ-017–REQ-022, the inherited REQ/NFR set and all acceptance thresholds remain unapproved. Phase 0 remains incomplete and product implementation remains unauthorized.
